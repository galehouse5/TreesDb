# 07 — Parity Verification

How we **prove** the new site matches the old one. This is the backbone of
the whole migration: every phase gate is defined here. Read this before
Phase 0 — snapshot capture happens while the legacy site is still live, and
several captures must be taken **before** any data freeze.

## 1. Principles

1. **The legacy app cannot run in this environment** (.NET Framework 4.5 /
   IIS / System.Drawing are Windows-bound). Therefore parity is established
   against (a) the **live legacy site** while it's up, and (b) **golden
   snapshots** captured from it and committed to the repo, so verification
   is deterministic, offline, and re-runnable forever after.
2. **Compare normalized semantic data, never raw HTML.** The two sites
   share no markup. Machine-readable surfaces (CSV, JSON) are compared
   nearly byte-wise; HTML pages are compared through per-page *extractors*
   that reduce both sites' pages to the same JSON shape.
3. **Float32 discipline.** Legacy stores `real` and formats through .NET
   float paths. All numeric comparison happens after coercing both sides
   to float32 (`Math.fround`); all formatted-string comparison uses the
   shared `web/lib/format.ts` implementation that itself works in float32.
4. **Intentional differences are waivered, never ignored.** A comparison
   failure is either a bug (fix it) or a decision (file `DECISIONS.md`
   entry + waiver in `web/parity/waivers.md`, which the comparator reads
   and reports as "waived", not "passed").
5. **Every category ends in a machine-readable report**
   (`web/parity/reports/<category>-<date>.json` + Markdown summary):
   counts of pass / fail / waived, and the first 50 diffs verbatim. Phase
   gates quote these reports.

## 2. Tooling layout

```
web/parity/
  corpus.ts          # builds corpus.json from the migrated DB (see §3)
  corpus.json        # committed: the list of URLs/entities under test
  capture.ts         # fetches legacy-site artifacts -> snapshots/ (see §4)
  verify.ts          # compares new app (or DB) against snapshots (see §5)
  extractors/        # per-page-type HTML -> JSON extractors, legacy + new
  normalize.ts       # shared normalization rules (§6)
  data/              # ETL data-parity checks (§7)
  replay/            # import replay-parity harness (§8)
  snapshots/         # committed golden files (public data only)
  dumps/             # GITIGNORED: raw production table dumps (PII)
  waivers.md         # waiver registry (§9)
  reports/           # generated; committed at phase gates
```

`capture.ts` and `verify.ts` are plain tsx scripts with `--category` and
`--base-url` flags. `verify.ts` exits non-zero on any unwaived failure.

Politeness: capture runs serially with a 250 ms delay between requests and
UA `treesdb-migration-parity/1.0`. It's our own low-traffic site; a full
capture is a few thousand requests. Capture is **idempotent and resumable**
(skips artifacts already on disk unless `--refresh`).

## 3. The corpus — what gets tested

Generated by `corpus.ts` **from the migrated Postgres data** (so it can be
regenerated identically offline) and committed as `corpus.json`. Contents:

- **All states** with `ComputedTreesMeasuredCount > 0`, plus 5 without.
- **All sites** (the registry has hundreds, not millions — full coverage is
  affordable).
- **All species** (global list from `Trees.MeasuredSpecies` grouping).
- **Trees, sampled**: top 100 by Height; top 50 by Girth; 150 uniformly
  pseudo-random with **fixed seed 424242** (document the PRNG: mulberry32
  over sorted tree Ids); plus targeted edge cases queried explicitly:
  - trees with unspecified coordinates (`LatitudeInputFormat = 1`)
  - trees with Invalid-format values (`InputFormat = 0`)
  - the tree with the most measurements
  - trees with photos; a multi-trunk-imported tree
  - species names containing `&`, `'`, `-`, `.`, non-ASCII, and the
    `(Unidentified)` placeholder
  - the site with the highest visit count; a site with exactly 4 species
    (below RHI5 threshold) and one with ≥ 20 (RHI20 populated)
- **Search terms**: 30 terms covering: exact state codes (`OH`, `USA`-style
  3-letter), state-name fragments, site-name prefixes/suffixes/infixes,
  species fragments hitting both botanical and common names, a term with
  zero hits, a term with > 25 hits, terms with `%`/`_` characters (LIKE
  metacharacters — parity check for escaping!), mixed case.
- **Autocomplete terms**: 10 per endpoint, incl. 1-character and no-match.
- **Grid states**: for each grid (Locations, Species, site-species,
  state-species, state-sites, species-trees), the default view plus every
  sortable column in both directions on page 0, one deep page, and one
  filtered view. Enumerated explicitly in corpus.json.
- **Units**: the whole export/detail corpus is captured under `Feet`; a
  20% subset is also captured under `Meters` and `Yards` (cookie
  `unitsPreference`) to pin unit conversion + formatting end to end.

## 4. Capture (run against the live legacy site)

`capture.ts --base-url https://treesdb.org` writes, per artifact, the raw
body plus a manifest entry `{url, status, contentType, sha256, capturedAt}`.

Categories:

| Category | Legacy request | Stored as |
|---|---|---|
| `exports` | the 8 export endpoints across the corpus (sites, states, species, filtered variants, plus `/Export/Trees/{id}` for sampled trees) | raw CSV |
| `markers` | `/Map/AllMarkers`, and `/Map/{id}/TreeMarker`, `/Map/{id}/SiteMarker` for corpus entities | raw JSON |
| `markerinfo` | `/Map/{id}/{State,Site,Tree}MarkerInfo` partials | raw HTML **and** extracted JSON |
| `search` | `/Search?term=…` with header `X-Requested-With: XMLHttpRequest` | raw JSON |
| `autocomplete` | both `/Trees/FindKnownSpecies…` endpoints | raw JSON |
| `pages` | detail pages (tree/site/species/state), Browse grids (HTML + AJAX partial responses with prefixed params), `/Browse/Activity` | raw HTML **and** extracted JSON |
| `photos` | `/Photos/{id}/{size}` for 20 corpus photos × all 11 sizes | content-type, byte length, and decoded pixel dimensions (via sharp) — **not** the bytes |
| `redirects` | `/`, `/Main`, legacy odds and ends | status + Location header |

HTML-derived categories store both raw HTML (for re-extraction if an
extractor changes) and the extracted JSON. Extractors for legacy pages live
in `web/parity/extractors/legacy/*.ts` (cheerio + CSS selectors against the
Razor markup — write them by reading the corresponding `.cshtml` views).

**Timing requirements:**
- Full capture happens in **Phase 0**, immediately after (or before) the
  ETL dump, so data and snapshots describe the same instant. If the site
  stays writable afterwards, note the divergence window; the final freeze
  in Phase 4 re-captures a delta set.
- Verify a captured sample by hand (5 artifacts) before bulk capture, to
  confirm selectors and auth assumptions (exports are anonymous — the
  anonymous session carries the Export role; see doc 01 §1).

## 5. Functional parity checks (new app vs snapshots)

`verify.ts --category <c> --base-url http://localhost:3000` replays each
corpus artifact against the new app (with the unit cookie where relevant)
and compares after normalization (§6).

### 5.1 `exports` — strongest oracle, target: byte-identical after normalization
The new CSV writer must reproduce: quoted-every-field, `""` escaping, CRLF,
the exact 25 columns and header strings (unit-dependent headers included),
`yyyy-MM-dd` dates, DDM coordinates, `Y`/`N` photos flag, and the filename
in `Content-Disposition`. Normalization for this category is minimal by
design: strip nothing except a trailing newline. A failure here almost
always means a real formatting or data bug. Target: **100% of corpus
artifacts identical** (row order: legacy emits repository order — pin the
new query to the same ORDER BY and document it; if unstable in legacy,
sort both sides by tree id in the comparator and record waiver W-003).

### 5.2 `markers` — JSON semantic equality
Parse both sides; compare with: key-order insensitivity; numbers compared
as float32; `Markers` array order-insensitively keyed by
(Title, Latitude, Longitude) — legacy order is repository order, new app
need not preserve it (waiver W-004 predeclared); `InfoLoaderUrl`/`IconUrl`
compared **by route-shape mapping** (legacy `/Map/5/TreeMarkerInfo` ↔ new
`/api/map/trees/5/info`), via a URL-equivalence table in `normalize.ts`.

### 5.3 `search` / `autocomplete` — ranked-results equality
Compare the ordered list of (Category, Subject, Url-equivalence) triples.
Rank ties: legacy tie-breaking is unspecified SQL order — comparator
treats **equal-rank groups as sets** (compute the rank per doc 01 §4
independently in the comparator to know the groups). The "Show more
results" / "No results found" message rows must appear under the same
conditions.

### 5.4 `pages` + `markerinfo` — extractor parity
For each page type an extraction schema is defined once, with two
implementations (legacy selectors / new selectors). Example, tree detail:

```jsonc
{
  "treeId": 123,
  "commonName": "White Oak", "scientificName": "Quercus alba",
  "site": {"name": "…", "url≡": "/Browse/Sites/45/Details"},
  "state": "Ohio", "county": "…",
  "height": "123.5'", "girth": "17.3'", "crownSpread": "88.0'",
  "elevation": "812.0 ft", "coordinates": "39.123 -84.456 …",
  "lastMeasured": "2018-05-12", "measurementCount": 3,
  "measurers": ["…"], "photos": 2,
  "measurements": [ {"measured": "…", "height": "…", "girth": "…"} ]
}
```

**Formatted strings are compared verbatim** — that is the point: it pins
unit conversion, float32 math, and format strings end-to-end. Extractors
must extract displayed text, not recompute it. Coverage: every field a
user can see on the page. Site/state/species pages likewise include their
Rucker indices (RHI/RGI 5/10/20 as displayed), counts, grid row contents
(first page: ordered list of row-cell text), and pagination totals.
Target: 100% of corpus pages, all fields equal or waivered.

### 5.5 `photos`
For each sampled photo × size: content-type equal; decoded dimensions
equal (fit/crop math per doc 01 §11 — including border widths); byte
length within ±20% (different encoder — informational only, waiver W-002
covers pixel-level difference).

### 5.6 `redirects` (Phase 4)
Every legacy URL pattern in the redirect map (doc 06) returns 301 to the
mapped new URL, including the species URLs containing spaces/parentheses
in both raw and percent-encoded forms, and `/` → `/map` behavior parity.

## 6. Normalization rules (shared, in `normalize.ts`)

- Numbers: parse → `Math.fround` → compare exactly. No epsilon comparisons
  anywhere — float32 coercion makes them unnecessary, and epsilons hide
  real formula drift.
- **Known hazard — midpoint rounding.** .NET custom format strings
  (`0.0`) round half-away-from-zero; JS `toFixed` is inconsistent at
  midpoints (binary representation). `format.ts` must implement explicit
  half-away-from-zero rounding (scale, add 0.5·sign, truncate — computed
  in float64 on the float32 input, matching .NET's internal widening).
  The formatting golden tests (§7.3) plus verbatim-string page parity
  will catch any residual divergence; each confirmed mismatch gets a
  micro-decision rather than a blanket epsilon.
- Dates: compare as ISO instants; legacy local-time serialization is
  mapped per D-002 (UTC).
- Whitespace: HTML extractors collapse internal runs and trim; CSV/JSON
  categories do NOT normalize whitespace.
- URL equivalence: single table mapping legacy route shapes ↔ new routes
  (also consumed by the Phase 4 redirect map — one source of truth).

## 7. Data parity (ETL correctness) — `web/parity/data/`

Run at the end of Phase 0 and re-run after the Phase 4 final sync.

### 7.1 Dump-based comparison
The dump procedure (doc 02 §4) produces one CSV per table from Azure SQL
with: explicit column list in schema order, `ORDER BY Id` (composite bags:
ORDER BY owner FK, Id), ISO 8601 datetimes (`CONVERT(varchar(33), col,
126)`), floats via `CONVERT(varchar(50), CAST(col AS float), 3)`
(17-digit round-trip), binary as lowercase hex. The comparator then, per
table:

1. **Row counts** equal.
2. **PK set equality** (report missing/extra Ids exactly).
3. **Field-by-field diff** of every row: strings byte-equal (no trimming —
   legacy semantics live in the data); floats parsed → fround → exact;
   datetimes as instants; booleans 0/1↔false/true; bytea hex-equal.
4. **Aggregate cross-check** (fast smoke, also used after delta syncs):
   per numeric column min/max/sum(float64)/null-count; per FK distinct
   count.
5. **Computed-column check**: recompute `ComputedMeasuredSpeciesId` in
   TypeScript (md5-last-4-bytes XOR — vector: `Quercus alba` + `White Oak`
   → `279197145`) for every Trees/Measurements row and compare to the
   dumped value. This validates the hash port used by species grouping.
6. **FK integrity**: every FK column in Postgres has its constraint
   validated (`NOT VALID` + `VALIDATE CONSTRAINT` pattern during load).

Target: zero diffs. `Logging.Errors` excluded. `Users` compared fully
(including hash bytes) but only aggregate results go in the committed
report.

### 7.2 Derived-data parity (the metric formulas)
Before migration, dump the legacy SQL objects' output — these are golden
files (public data, committed):
`SiteMetrics`, `StateMetrics`, `MeasuredSpecies`, `MeasuredSpeciesBySite`,
`MeasuredSpeciesByState`, `MeasurerActivity`, each `ORDER BY` its id
column, plus the three search TVFs evaluated over the corpus search terms
(`SELECT * FROM dbo.SearchSites('oak') ORDER BY Id`, …).
The new implementations (Postgres views/queries) are then evaluated
against the migrated data and compared row-for-row (float32 rule). This
**directly pins the Rucker index, species aggregation, and search-ranking
ports** with production-scale data, independent of any UI.
Also compare `Computed*` columns on Sites/States after running the new
recompute job from scratch (set all stale → recompute → compare against
dumped Computed* values).

### 7.3 Formatting & algorithm golden tests (unit tests, run in CI forever)
`web/lib/**` test suites seeded from doc 01:
- Password vectors (doc 01 §6.1, all four) + trim-asymmetry cases.
- SecureToken codec vectors (doc 01 §6.3) + round-trip property test.
- Unit formatting: the reference table (doc 01 §7) plus, generated during
  capture, **200 real formatted values scraped from legacy pages** with
  their float32 inputs from the dump — this grounds the suite in actual
  legacy output, not our reimplementation of it.
- Species-hash vector; DDM/DMS coordinate formatting; height-from-
  clinometer formula; conical volume; planar distance; Rucker struct
  formatting (2 dp vs 3 dp).

## 8. Import replay parity (Phase 3 gate) — `web/parity/replay/`

The strongest possible oracle for the merge algorithm, exploiting two
legacy facts: (a) finished trips remain fully populated in `Imports.*`,
and (b) every merged row is tagged `ImportingTripId`
(`Trees.Measurements`, `Sites.SiteVisits`).

**Replay check** — for each historical imported trip T (every trip with
`Imported IS NOT NULL`):
1. Create a disposable copy of the migrated DB (Neon branch — cheap,
   instant; or local Postgres template DB).
2. Run the new **Reimport** code path for T: delete T's measurements and
   visits (with the same orphan-cleanup rules as legacy —
   `RemoveMeasurementsByTrip` / `RemoveVisitsByTrip`), then run the new
   import/merge on T's `Imports.*` rows.
3. Diff the resulting DB against the pre-replay state: the replay must
   reproduce **exactly** the rows previously attributed to T (same
   measurements on the same trees, same visits on the same sites, same
   recomputed tree/site properties and metrics), and leave everything
   else untouched. Compare by natural keys, not identity ids.
4. Drop the branch.

Rationale: legacy `Reimport` is delete-then-import with the same merge
code; if our merge is faithful, replay is a fixed point. Expected
imperfection: a small number of trips may mismatch because site/tree data
was hand-edited after import or the site-matching context changed since
the original import. Each mismatching trip is investigated individually;
outcomes are either a merge-code bug (fix) or a documented data-drift
waiver naming the trip (W-1xx series). **Gate: 100% of trips replay
clean or carry an investigated, named waiver.**

**Synthetic merge suite** (unit/integration tests, complements replay):
constructed fixtures asserting each rule in doc 01 §10 —
site matched at 24.9′ vs missed at 25.1′; name match but county mismatch
→ new site; tree merged on exact float32 coordinate equality, not merged
on 1-ulp difference or unspecified coords; measurements accumulate;
visitor dedup; `(Unidentified)` default; reimport idempotence
(reimport twice ≡ once); metrics stale-flag propagation.

**Wizard UI parity** is not snapshot-testable (auth + statefulness);
it is covered by the synthetic suite + a scripted Playwright walkthrough
of a real historical trip's data entered end-to-end, asserting the
resulting DB rows equal that trip's replay output.

## 9. Waivers — `web/parity/waivers.md`

```
## W-00X: <title>
- Category / artifacts affected: exports | markers | … (glob or list)
- Field(s):
- Legacy behavior / new behavior:
- Reason: <decision D-0YY link>
- Comparator rule: <exact normalization or skip applied>
- Approved by: <repo owner> on <date>
```

Predeclared: W-001 species max-tree tie-breaking (lowest Id), W-002 photo
pixel-level difference (dimensions/type still compared), W-003 export row
order (only if legacy order proves unstable), W-004 marker array order.
**Every other waiver requires repo-owner approval before merging.** The
comparator loads waivers and reports them in a distinct "waived" bucket —
a waiver never turns a check green silently.

## 10. Phase gates (summary)

| Gate | Required green |
|---|---|
| **Phase 0 exit** | §7.1 zero diffs on all tables; §7.2 all six views + search TVFs row-identical; §7.3 suites green; full snapshot capture complete & manifest committed |
| **Phase 1 exit** | §5.1 exports 100%; §5.2 markers 100%; §5.3 search + autocomplete 100%; §5.4 all corpus pages/markerinfo 100% (waivers listed); §5.5 photos |
| **Phase 2 exit** | password + token vector suites green; migrated fixture users (copies of real hash rows with emails swapped for test addresses) log in; wrap-and-rehash proven by second login using argon2 path; reset-token expiry/single-use tests |
| **Phase 3 exit** | §8 replay parity 100% (or named waivers); synthetic merge suite green; Playwright wizard walkthrough green; §7.2 re-run green after merge code landed |
| **Phase 4 exit** | §5.6 redirects 100%; final delta sync then §7.1 aggregates re-run green; production smoke of §5.1/§5.2 against the live new site |

## 11. Honest limits — what this does NOT prove

Keep these visible; they bound the confidence claim:

- **Snapshot coverage = corpus coverage.** Pages/IDs outside the corpus are
  verified only transitively (same code paths). Mitigation: corpus covers
  100% of sites/states/species and all edge-case classes we could
  enumerate; add to the corpus whenever a bug reveals a missing class.
- **Behavior under concurrent writes** isn't snapshot-testable; the import
  path is single-user-low-volume and covered by the synthetic suite only.
- **The formatting vectors in doc 01 were computed from our reading of the
  legacy code**, not from running it. The scraped-from-production
  formatting tests (§7.3) and verbatim-string page parity (§5.4) are the
  authoritative cross-check; where a vector disagrees with a scraped
  value, production wins — update the vector and note it.
- **Email delivery** is contract-tested (correct link URLs, token codec)
  but not parity-tested against legacy SMTP output.
